## Chapter 7: Data Ingestion, Storage, and Pipeline Architecture — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | ETL vs ELT — where does transformation happen? | ETL: transform before loading into target (external engine). ELT: load raw data first, transform inside the target system (e.g., cloud warehouse compute). Exam tip: ELT is preferred with modern cloud warehouses due to scalable compute. |
| 2 | Data lake vs data warehouse — schema timing? | Data lake = schema-on-read (structure applied at query time). Data warehouse = schema-on-write (structure enforced at load time). Exam tip: lakes store raw/unstructured data cheaply; warehouses store curated, structured data. |
| 3 | What is a lakehouse? | Architecture combining data lake storage (cheap files, e.g., S3/ADLS) with warehouse features: ACID transactions, schema enforcement, time travel (e.g., Delta Lake, Apache Iceberg). Exam tip: chosen when you need BI query performance + raw data flexibility in one system. |
| 4 | Batch vs streaming ingestion — latency profile? | Batch: processes data in scheduled chunks (minutes to hours latency). Streaming: processes events continuously (sub-second to seconds latency). Exam tip: choose streaming when the scenario mentions 'real-time' or specific low-latency SLAs. |
| 5 | Schema drift — definition | Unplanned, unexpected changes to a data source's structure (new/removed/renamed fields, type changes) that can break downstream pipelines if not handled. Exam tip: distinguish from schema evolution, which is the managed response to drift. |
| 6 | Schema evolution — definition | A pipeline's deliberate policy/mechanism for accommodating schema changes (e.g., allow new nullable columns, schema registry compatibility modes: BACKWARD, FORWARD, FULL). Exam tip: additive changes are usually safe; type changes or removals often break compatibility. |
| 7 | Idempotency in pipeline design | A task/operation that produces the same end state no matter how many times it runs (e.g., MERGE/UPSERT instead of INSERT). Exam tip: retries in orchestration tools (Airflow, etc.) require idempotent tasks to avoid duplicate data. |
| 8 | Delta Lake default log retention duration | 30 days (delta.logRetentionDuration). Controls how long transaction log history is kept for time travel queries. Exam tip: don't confuse with VACUUM's default file retention. |
| 9 | Delta Lake default VACUUM file retention | 7 days (delta.deletedFileRetentionDuration). Files older than this can be permanently deleted by VACUUM. Exam tip: running VACUUM with a shorter retention risks breaking active time-travel queries. |
| 10 | Apache Kafka default message retention | 168 hours (7 days), set via log.retention.hours. Exam tip: streaming pipelines must consume before retention expires or data is lost from the topic. |
| 11 | CDC (Change Data Capture) — purpose | Captures row-level insert/update/delete events from a source database (often via transaction/binlog reading) to feed downstream pipelines incrementally instead of full reloads. Exam tip: CDC enables near-real-time ELT without re-scanning entire source tables. |
| 12 | Embedded data quality checks — common pipeline pattern | Validate schema, null rates, uniqueness, and value ranges at ingestion/transform stages (e.g., using frameworks like Great Expectations) BEFORE data reaches production tables. Exam tip: quality gates should fail/quarantine bad records rather than silently loading them. |
